# OMIC-16: internal capture in the existing Collector SQLite

Status: implementation plan for adversarial review. No OMIC-16 code or production migration has begun. This plan does not authorize changing the public ready format or the external ACK protocol.

## Goal and observable boundary

The Collector currently stores private attempt, quarantine, and draft audio in `records.bin` files while its control state is in `collector-state.sqlite3`. The operator approved moving **only internal work** into that existing SQLite. Public `ready/<bundle-id>/records.bin` and `manifest.json` stay ordinary immutable files retrievable by any consumer; their names, bytes, manifest schema, UTC behavior, and ACK checkpoint remain compatible. The stable zero-content `collector.lock` remains the sole singleton lock. No archive, fallback raw writer, second permanent database, optional backend, or new alarm for known small firmware losses is part of this change.

The 2026-10-13 live reference was 124 working files: 94 ready output files (47 pairs), 28 draft files (14 pairs), the SQLite file, and the lock. On that fixed snapshot, successful consolidation yields 96 files: the same 94 output files plus SQLite and lock. Actual live counts may change during capture; acceptance reconciles each category and verifies zero private attempt/draft/quarantine audio files, rather than treating 96 as a timeless absolute. Transient SQLite journal files and the single owned recoverable ready-output stage are classified separately.

## Existing contracts and implementation reach

The read path is `application/collector.py` → `domain/transfer_arena.py` → `adapters/attempt_writer.py` (one writer thread) → `adapters/staging_writer.py` → `adapters/attempts.py`. The writer drains up to 128 complete records per call; the configured durability cadence is 1,024 records, with explicit barriers. A ring record is exactly 444 bytes: the original four-byte **big-endian** device timestamp and 440 exact payload bytes. Notifications may split a record arbitrarily. `READ_BEGIN` must bind the prepared range before DATA. The current attempt raw/checkpoint path is in `attempts.py` and `staging_filesystem.py`; `staging_store.py` composes capture and publication. `opportunistic_runtime.py`, `application/ports.py`, `application/batch_reconciliation.py`, `application/session_lifecycle.py`, `cli.py`, and status/metrics callers consume those contracts.

`adapters/ready_bundles.py` authenticates draft and ready files, normalizes overlapping sources, groups physical continuity, requires a drained closure plus `ceil(target_audio_seconds * 50)` packets, converts timestamps through the existing clock segment mapper, writes/fsyncs/renames public output, then commits the ready ledger. It retires output only after exact external ACK `(bundle_id, records_sha256)` and open-speech-tail preflight. Preserve these semantics and the existing `ready_machine.py` decisions. Replace the draft-file input and UUID scratch only. `adapters/publication.py`, `quarantine.py`, `attempt_cleanup.py`, `staging_contract.py`, `staging_filesystem.py`, `staging_store.py`, `storage_layout.py`, `spool_metrics.py`, and operator-status/CLI views must be audited so no active private-file writer, reader, cleanup, or stale metric remains.

`collector_state_db.py` currently has schema version 1 and one generic JSON `state(kind,id,payload)` table, DELETE journal mode, `synchronous=EXTRA`, a 5-second busy timeout, and a per-call connection. Production's existing metadata, ready ledger, clock state, quality rows, and migration marker must survive an additive version-2 schema. `state_migration.py` currently migrates only control files, not raw audio. `scripts/deploy-systemd-service.sh` stops the service, runs staged `migrate-state`, switches the release, and has rollback/finalize traps; that rollback path is part of the change.

## Typed model and durability contract

Add typed tables to the **same** SQLite, while retaining the existing metadata table: `capture_source` (identity, source type, lifecycle, unsigned sequence start and limit, prepared/read-begin range, committed count/SHA, durable tail offset, closure and block reason), `capture_record` (source identity + ordinal primary key, queryable original `device_timestamp` INTEGER constrained to uint32, exact 440-byte payload BLOB, nullable queryable derived `utc_timestamp` INTEGER, and mapping revision), `capture_tail` (one source/leg/high-water-bound fragment of 1–443 bytes at an exact byte offset), `capture_conflict` (bounded exact rejected bytes, offset/source/leg and reason, never overwriting accepted evidence), `publication_cohort` (durable accepted permit, closure frontier, threshold/config observed, ordered source/slice membership and progress), and `ready_output_stage` (one deterministic owned active output intent, expected bundle identity/digest/ranges, progress and ownership). Names can change in code, but each field and invariant must have a typed, checked representation; opaque JSON audio blobs or a second DB are unacceptable. `CHECK` constraints enforce uint32 device and UTC timestamp ranges, 440-byte payload, tail bound, and nonnegative ordinal. Store uint64 sequence values losslessly as fixed-width eight-byte big-endian BLOBs (or an equivalently proved encoding), with explicit Python boundary validation and lexicographic ordering; never narrow them through SQLite signed INTEGER. Ordinal/count fits the protocol's uint32 bound. Reconstruct exact original bytes as `device_timestamp.to_bytes(4, "big") + payload` and compare streaming SHA-256 and count to the source checkpoint. Refresh derived UTC for unpublished rows from the existing clock mapper when its revision changes and again before freezing an output-stage mapping; `NULL` with a current revision denotes an unknown/unrepresentable UTC mapping. This is a queryable projection, not a second source of original truth or a global clock/provenance snapshot. Original device timestamps and payloads never change, and already published ready remains immutable.

The writer thread remains the only capture SQL writer. It buffers at most the configured checkpoint quantum of complete records plus one <444-byte tail, drains the existing 128-record delivery chunks without treating each as a durability guarantee, and commits every 1,024 records and on explicit checkpoint, close, seal, or interruption barriers. **One transaction** inserts the complete rows and exact tail, updates checkpoint count/SHA and source lifecycle/high-water, and only then returns a durable frontier to the caller. It holds no SQLite transaction across a BLE await. Extend the arena/writer target seam to hand an immutable snapshot of the incomplete record and its exact source/leg/byte offset to the writer at barriers; the current complete-record-only API cannot meet this requirement. On replay, compare saved tail bytes before completing that record; preserve mismatching incoming bytes in typed conflict evidence and block the source without rewriting accepted data. A committed tail never advances the complete-record sequence frontier.

If `COMMIT` reports an ambiguous failure, close and reopen the authoritative DB and compare the proposed count, SHA, tail, and rows before acknowledging it. If the comparison cannot establish exact commit or rollback, fail stop. Disk-full, corruption, busy timeout, or any DB failure prevents seal success and pendant `ADVANCE`; do not silently create an empty replacement DB or write fallback raw. A validated full seal must be committed before the existing `ADVANCE` command is sent. The existing single-process guard covers every mutating/BLE command; read-only status may inspect the database without taking the flock.

## Total lifecycle decisions

The implementation must encode and test this total transition matrix. `REFUSE` means deterministic no-mutation rejection; an unexpected data conflict instead uses `BLOCK` and retains exact evidence. `INTERRUPTED` means a recoverable interrupted transfer, while `SEALED_WAITING` means a complete validated DONE source or durably terminalized prefix awaiting publication; these names avoid confusing transport recovery with product-level pending audio. `RETIRE` is allowed only when every unique physical record has authenticated durable ready custody/lineage (or an explicit zero-record terminal source). It deletes private rows in the same SQL transaction that finalizes the corresponding ledger/coverage facts, after public files are durable.

| Current state | prepare | matching READ_BEGIN / resume | matching record or replay | barrier | validated DONE / terminal prefix | interruption | conflict | full ready custody |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| absent | prepared | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE |
| prepared | REFUSE | receiving | REFUSE | prepared (durable zero prefix) | REFUSE | interrupted | blocked | REFUSE |
| receiving | REFUSE | REFUSE | receiving | receiving (commit) | sealed_waiting (commit) | interrupted (commit) | blocked | REFUSE |
| interrupted | REFUSE | receiving after bounded replay check | REFUSE | interrupted | sealed_waiting only with authenticated prefix | interrupted | blocked | REFUSE |
| sealed_waiting | REFUSE | REFUSE | REFUSE | sealed_waiting | sealed_waiting (idempotent identity) | sealed_waiting | blocked only on newly authenticated conflict | RETIRE when all unique coverage is ready |
| blocked | REFUSE | REFUSE | REFUSE | blocked (inspect only) | REFUSE | blocked | blocked | REFUSE |

The implementation must also enumerate every publication-cohort state/event pair: unqualified input waits; drained qualified input atomically records one accepted permit and frozen ordered membership **before the first output**; accepted/staging retries reconcile the same permit and stage; each durable output plus ledger advances the cohort cursor; after all groups and custody checks, the cohort and covered source rows retire. An impossible or conflicting transition blocks without deleting evidence. A 2,000-second group followed by a 1,600-second group under a 3,600-second threshold must finish after a crash following the first output, because the persisted permit applies to the whole accepted cohort; do not reapply the threshold to the remainder. Subthreshold input without a drained qualification waits indefinitely as today. Preserve closure frontier, overlap/gap normalization, complete payload equality, no double publication, and immutable output/ACK behavior.

## Ready-output crash protocol

Before writing a public group, persist a stage intent keyed deterministically by its accepted cohort and bundle identity, including its frozen source slice geometry and time ranges for that output. Use one owned hidden staging directory/pair for the active group, not `.bundle.<uuid>.tmp` litter. Stream original DB rows in bounded chunks, apply the existing UTC conversion, write `records.bin`, fsync it, write the unchanged canonical manifest, fsync the directory, rename to the final ready name, then fsync the ready parent. Only after this durable boundary commit the existing ready ledger identity/lineage and advance the cohort; only after verified complete coverage delete private source records. Startup/retry first reconciles the deterministic stage and any already durable destination against the SQL intent, output hashes, manifest, and ledger. It may resume or rebuild only an **owned authenticated** incomplete stage; an unknown or unowned file/dir is preserved and causes a clear block. The output stage is removed after a finished group; there is never unbounded hidden scratch accumulation. Existing ready files are never rewritten, and ACK retirement remains ledger-first and exact-identity guarded.

## Guarded one-way migration and deployment

Implement a version-1-to-2 stopped-service migration under `collector.lock`, using one transient same-filesystem candidate database. First inventory and fingerprint every old private attempt, draft, and quarantine file and relevant metadata; reject unknown paths, symlinks, changing identities, incomplete manifests, or unsupported opaque evidence. Authenticate each old manifest/checkpoint/raw byte stream, including a possible aligned uncheckpointed suffix and a bounded unaligned tail, then import source/ordinal rows and typed tail/conflict evidence in bounded chunks. Preserve overlapping sources separately so equality/conflict and physical gaps remain testable. Copy the version-1 SQLite with its existing state rows into the candidate, add the typed schema, import, and verify candidate integrity and per-source reconstructed byte count/SHA, checkpoint/frontier, source order, gap/overlap graph, closure/ready lineage, and ready bytes where a draft is already covered. Run a semantic parity pass against the old files before activation. Never use a memory-sized full raw read. Preflight candidate disk space and account for actual peak file/database usage.

Activate the fully verified candidate atomically, fsync the directory, then revalidate recorded file identities/hashes and delete **only** the exact obsolete private files. Mark cleanup complete only after the files and directories have been reconciled; interrupted cleanup resumes forward from the version-2 DB and fingerprint list, without guessing or deleting unknown paths. The runtime gate refuses a version-2 DB with pending/unknown legacy internal files until cleanup is reconciled. The version-1 DB and raw files remain intact before candidate activation, so a pre-activation failure can use the old release after safely classifying/removing only our transient candidate. **Candidate activation is the irreversible compatibility boundary:** the old binary cannot open schema version 2 even if raw files have not yet been removed. From that point the deploy trap must retain/select the new compatible release and fail stopped until forward migration/cleanup succeeds; it must never auto-restart the old binary. After deletion, rollback means a new-schema-compatible fix/rollforward, not restoration of old raw. Review and update the actual `scripts/deploy-systemd-service.sh` finalize/rollback branch, CLI `migrate-state`, install/permissions, and its tests accordingly. No archive or permanent legacy backend remains; offline migration decoders may remain isolated from runtime until a future intentional removal.

Physical SQLite corruption is a fail-stop condition that preserves the database and its journal for recovery; do not claim that a row in the same damaged DB can quarantine it. Validate service-account read/write ownership and operator-group read-only access after candidate activation. The ready output tree and downstream `work/omi-ready-checkpoint.json` stay outside the internal migration. Do not touch production before the code, tests, peer review, PR, and protected release candidate pass.

Confirm an actual post-deploy capture/checkpoint/publication scenario when the pendant provides one; if no new audio arrives, report that limit explicitly rather than claiming an exercised capture path.

## Review questions that must be resolved before code

The cross-AI review should stress the exact-byte tail handoff between the arena and writer, whether the proposed source/ordinal schema and `CHECK` constraints capture all legacy quarantine evidence without a second raw blob, the commit-ambiguity decision rule, cohort membership when clock observations or new sources arrive mid-publication, and deterministic stage ownership after a hard kill. It should also challenge the deployment boundary against the real finalize trap and prove which state can safely restart the old binary. Any unresolved conflict must be settled in this plan and reviewed again before implementation.
