# OMIC-16: internal capture in the existing Collector SQLite

Status: implementation plan for adversarial review. No OMIC-16 code or production migration has begun. This plan does not authorize changing the public ready format or the external ACK protocol.

## Goal and observable boundary

The Collector currently stores private attempt, quarantine, and draft audio in `records.bin` files while its control state is in `collector-state.sqlite3`. The operator approved moving **only internal work** into that existing SQLite, with a forward-only cutover and no old-release rollback or retained archive. Public `ready/<bundle-id>/records.bin` and `manifest.json` stay ordinary immutable files retrievable by any consumer; their names, bytes, manifest schema, UTC behavior, and ACK checkpoint remain compatible. The stable zero-content `collector.lock` remains the sole singleton lock. No archive, fallback raw writer, second permanent database, optional backend, or new alarm for known small firmware losses is part of this change.

The 2026-10-13 live reference was 124 working files: 94 ready output files (47 pairs), 28 draft files (14 pairs), the SQLite file, and the lock. On that fixed snapshot, successful consolidation yields 96 files: the same 94 output files plus SQLite and lock. Actual live counts may change during capture; acceptance reconciles each category and verifies zero private attempt/draft/quarantine audio files, rather than treating 96 as a timeless absolute. Transient SQLite journal files and the single owned recoverable ready-output stage are classified separately.

## Existing contracts and implementation reach

The read path is `application/collector.py` → `domain/transfer_arena.py` → `adapters/attempt_writer.py` (one writer thread) → `adapters/staging_writer.py` → `adapters/attempts.py`. The writer drains up to 128 complete records per call; the configured durability cadence is 1,024 records, with explicit barriers. A ring record is exactly 444 bytes: the original four-byte **big-endian** device timestamp and 440 exact payload bytes. Notifications may split a record arbitrarily. `READ_BEGIN` must bind the prepared range before DATA. The current attempt raw/checkpoint path is in `attempts.py` and `staging_filesystem.py`; `staging_store.py` composes capture and publication. `opportunistic_runtime.py`, `application/ports.py`, `application/batch_reconciliation.py`, `application/session_lifecycle.py`, `cli.py`, and status/metrics callers consume those contracts.

`adapters/ready_bundles.py` authenticates draft and ready files, normalizes overlapping sources, groups physical continuity, requires a drained closure plus `ceil(target_audio_seconds * 50)` packets, converts timestamps through the existing clock segment mapper, writes/fsyncs/renames public output, then commits the ready ledger. It retires output only after exact external ACK `(bundle_id, records_sha256)` and open-speech-tail preflight. Preserve these semantics and the existing `ready_machine.py` decisions. Replace the draft-file input and UUID scratch only. `adapters/publication.py`, `quarantine.py`, `attempt_cleanup.py`, `staging_contract.py`, `staging_filesystem.py`, `staging_store.py`, `storage_layout.py`, `spool_metrics.py`, and operator-status/CLI views must be audited so no active private-file writer, reader, cleanup, or stale metric remains.

`collector_state_db.py` currently has schema version 1 and one generic JSON `state(kind,id,payload)` table, DELETE journal mode, `synchronous=EXTRA`, a 5-second busy timeout, and a per-call connection. Production's existing metadata, ready ledger, clock state, quality rows, and migration marker must survive an additive version-2 schema. `state_migration.py` currently migrates only control files, not raw audio. `scripts/deploy-systemd-service.sh` currently stops the service, runs staged `migrate-state`, then switches the release; this order and its rollback/finalize trap must be replaced with a forward-only selector-first cutover.

## Typed model and durability contract

Let `K` be the validated active `writer.chunk_records` (currently 128); every capture drain, conflict chunk, ready read page and bounded UTC refresh quantum uses `K`, with an explicit configured upper bound. Add typed tables to the **same** SQLite, while retaining the existing metadata table: `capture_source` (identity, source type, lifecycle, unsigned sequence start and limit, prepared/read-begin range, committed count/SHA, closure/block reason, quarantine terminal state/reason/time and retention deadline), `capture_record` (source identity + ordinal primary key, queryable original `device_timestamp` INTEGER constrained to uint32, exact 440-byte payload BLOB, nullable queryable derived `utc_timestamp` INTEGER, and mapping revision), `capture_tail` (**at most one row per source**, with leg/high-water identity, exact byte offset and 1–443 bytes), `capture_conflict` (exact rejected bytes split into bounded chunks of at most one `K`-record drain, offset/source/leg and reason, never overwriting accepted evidence), `capture_evidence` (typed legacy opaque/quarantine entry kind, owned path, inode identity, terminal state/reason/time and bounded byte chunks or symlink link text without following the link), `publication_cohort` (durable accepted permit, closure frontier, threshold/config observed, ordered source/slice membership and progress), and `ready_output_stage` (one deterministic owned active output intent, expected bundle identity/digest/ranges, progress and ownership). Names can change in code, but each field and invariant must have a typed, checked representation; opaque JSON audio blobs or a second DB are unacceptable. `CHECK` constraints enforce uint32 device and UTC timestamp ranges, 440-byte payload, tail bound, and nonnegative ordinal. Store uint64 sequence values losslessly as fixed-width eight-byte big-endian BLOBs (or an equivalently proved encoding), with explicit Python boundary validation and lexicographic ordering; never narrow them through SQLite signed INTEGER. Ordinal/count fits the protocol's uint32 bound. Reconstruct exact original bytes as `device_timestamp.to_bytes(4, "big") + payload` and compare streaming SHA-256 and count to the source checkpoint. Keep both timestamp columns queryable by ordinary SQLite clients. `device_timestamp` is authoritative; `utc_timestamp` is a nullable materialized projection paired with a clock-specific `mapping_revision`: SHA-256 of the canonical JSON bytes of `state(kind='clock', id='current')` (or canonical `ClockState()` payload when absent), separate from `publication_generation`. The current revision is recomputed from that same authoritative CLOCK payload on read/refresh, so `mapping_revision != current_clock_hash` is the stale predicate; clients can read the payload and revision with ordinary SQLite and compute the hash without a DB extension or hidden UDF. A clock revision change does not synchronously rewrite rows: a row with a stale revision is visibly stale and must not be treated as current UTC; `NULL` at the current revision means unknown or unrepresentable UTC. Existing idle maintenance may refresh stale unpublished rows in keyset pages of at most `K` rows, each in its own short transaction, yielding to active BLE capture without a new timer or clock-history store; a projection-only update does not bump `publication_generation`. A real CLOCK payload change still bumps publication generation under the existing publication-wake contract. The current `ClockSegmentMap`, not this cache, freezes output-stage time ranges; no whole-backlog projection refresh is required before ready publication. Reserve for one worst-case `K`-row refresh transaction in the steady-state space preflight and test stale/current client queries and concurrent capture. This is a queryable projection, not a second source of original truth or a global clock/provenance snapshot. Original device timestamps and payloads never change, and already published ready remains immutable.

The writer thread opens, owns, and closes one persistent SQLite connection on that same thread; its capture transaction helpers use that connection without nested `StateDB` calls that open a second writer connection. An ambiguous COMMIT closes it and reopens the authoritative DB before comparison. Status uses separate per-call read-only connections and closes each read transaction promptly. The writer thread remains the only capture SQL writer. Every delivered drain of **up to `K` complete records, including a shorter drain**, is one short committed transaction: rows, count/SHA checkpoint, and frontier-compatible tail state are atomic. It closes the transaction before the thread returns to its idle wait; no transaction stays open while BLE is idle or any other StateDB writer runs. The old 1,024-record setting was a raw-file fsync/checkpoint cadence, not the recoverable-byte boundary; remove `durability.checkpoint_records` from the new active config/schema/templates/docs/callers instead of retaining a periodic verification fiction. The explicit `checkpoint()` API still drains its captured high-water and tail and returns the committed prefix. Legacy import reads old recorded checkpoint metadata without requiring that knob at runtime. This matches the old raw writer's process-kill survival of each delivered aligned chunk; the former raw file wrote each drain immediately and promoted its aligned tail on restart even before its 1,024-record fsync/checkpoint. A power-loss guarantee is separately measured, not inferred from process-kill behavior. If measured per-drain SQLite commits cannot keep up with the largest real batch, revise and re-review the durability design before relaxing it; do not silently widen confirmed-loss exposure.

Synchronously **before any await** at command admission on the event-loop thread, copy immutable `(source_id, leg_generation, complete-record high-water, absolute received high-water, exact tail offset, tail bytes)` from the loop-owned `TransferArena`; the writer must never read a mutable live tail. The arena's existing replay comparison leaves bytes below the captured received watermark immutable. The writer drains only the captured complete high-water and acknowledges each committed frontier after COMMIT. When one snapshot spans several ≤`K`-record transactions, intermediate commits clear a prior tail only when newly committed complete rows cover its byte interval, and contain no tail beyond their committed complete frontier; only the final transaction that reaches the snapshot frontier may attach its exact captured tail. A shorter matching replay at the same frontier retains the longer previously committed tail. Every stored tail offset equals its transaction's committed complete-record byte frontier, and no writer-thread read of a mutable live tail is allowed. On a recovery leg, a shorter incoming replay compares against only the incoming prefix and **retains** the longer saved tail; equal replay may extend it, and a mismatch stores the exact rejected bytes in typed conflict evidence and blocks without overwriting accepted bytes. One tail row is atomically replaced with the source frontier, never accumulated per leg. A committed tail never advances the complete-record sequence frontier. `PREPARE_LEG` is its own durable event: it bounds the new leg within the immutable source snapshot, permits replay start no later than the durable next sequence, increments `leg_generation`, and stores its start/count before issuing READ. If called while receiving, it first commits the current barrier/interruption in the same short transaction. A matching-generation `READ_BEGIN` then re-enters receiving; DATA before it is refused. An exact duplicate READ_BEGIN for the current generation is idempotent only where the current adapter already permits it.

If `COMMIT` reports an ambiguous failure, close and reopen the authoritative DB and compare the proposed count, SHA, tail, and rows before acknowledging it. If the comparison cannot establish exact commit or rollback, fail stop. SQLite busy contention gets bounded retry/backoff on the writer thread with a finite measured deadline; ordinary concurrent clock/quality writes and read-only status must complete without exhausting it, while an overlong reader or damaged DB fails deterministically and prevents `ADVANCE`. Disk-full, corruption, or any unresolved DB failure prevents seal success and pendant `ADVANCE`; do not silently create an empty replacement DB or write fallback raw. A validated full seal must be committed before the existing `ADVANCE` command is sent. The existing single-process guard covers every mutating/BLE command; read-only status may inspect the database without taking the flock.

## Total lifecycle decisions

The implementation must encode and test this total transition matrix. `REFUSE` means deterministic no-mutation rejection; an unexpected data conflict instead uses `BLOCK` and retains exact evidence. `INTERRUPTED` means a recoverable interrupted transfer, while `SEALED_WAITING` means a complete validated DONE source or durably terminalized prefix awaiting publication; these names avoid confusing transport recovery with product-level pending audio. `RETIRE` is allowed only when every unique physical record has authenticated durable ready custody/lineage (or an explicit zero-record terminal source). After public files are durable, commit ledger/coverage proof and a typed `RETIRING` cursor; delete covered rows in bounded transactions and resume from that cursor after a crash. Retaining source bytes until downstream external ACK is unnecessary: ACK governs **public ready output** retirement, not private source custody. A blocked source may retain certified salvage-prefix rows awaiting ready custody and separate residual evidence awaiting its retention deadline.

| Current state | create source | PREPARE_LEG | matching READ_BEGIN | matching record/replay | barrier | validated DONE / terminal prefix | interruption | conflict | full ready custody |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| absent | prepared | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE | REFUSE |
| prepared | REFUSE | leg_prepared | REFUSE | REFUSE | prepared (durable zero prefix) | REFUSE | interrupted | blocked | REFUSE |
| leg_prepared | REFUSE | exact identity idempotent, else REFUSE | receiving | REFUSE | leg_prepared | REFUSE | interrupted | blocked | REFUSE |
| receiving | REFUSE | leg_prepared after atomic barrier and bounded leg check | REFUSE except permitted same-generation retry | receiving | receiving (commit) | sealed_waiting (commit) | interrupted (commit) | blocked | REFUSE |
| interrupted | REFUSE | leg_prepared after bounded leg check | REFUSE | REFUSE | interrupted | sealed_waiting only with authenticated prefix | interrupted | blocked | REFUSE |
| sealed_waiting | REFUSE | REFUSE | REFUSE | REFUSE | sealed_waiting | sealed_waiting (idempotent identity) | sealed_waiting | blocked only on newly authenticated conflict | RETIRE when all unique coverage is ready |
| blocked | REFUSE | REFUSE | REFUSE | REFUSE | blocked (inspect only) | REFUSE | blocked | blocked | REFUSE; certified salvage prefix uses the separate quarantine disposition FSM |

The separate retirement sub-FSM is `COVERED` (durable ready files + ledger/lineage) → `RETIRING(cursor)` → absent. Only a bounded, idempotent delete step may advance a `RETIRING` cursor; capture, replay, cohort admission, and ACK events refuse in that state. Each chunk deletes at most the measured safe row quantum, and the final chunk removes the source metadata after confirming the stored coverage proof. A crash at any cursor resumes from the authoritative SQL rows. The quarantine disposition FSM below owns residual evidence independently from certified audio coverage.

The publication-cohort FSM has these exhaustive state/event decisions: `UNQUALIFIED` + no drained threshold → wait; `UNQUALIFIED` + drained qualified threshold → atomically `ACCEPTED` with ordered source/slice membership and observed threshold before the first output; `ACCEPTED` + next group → `STAGING`; `STAGING` + owned incomplete output → reconcile/rebuild the same group; `STAGING` + durable destination → ledger commit and advance the cohort cursor to `ACCEPTED` or `COMPLETE`; `COMPLETE` + all unique coverage proved → retire cohort and covered source rows; other event/state pairs refuse without mutation. A 2,000-second group followed by a 1,600-second group under a 3,600-second threshold must finish after a crash following the first output, because the persisted permit applies to the whole accepted cohort; do not reapply the threshold to the remainder. New sources arriving after permit creation are a later cohort, not silently added to the frozen membership. Existing clock observations can refresh only **unpublished** groups; once a group gets a stage intent, its range mapping is frozen for deterministic retry. Subthreshold input without a drained qualification waits indefinitely as today. Preserve closure frontier, overlap/gap normalization, complete payload equality, no double publication, and immutable output/ACK behavior. Bump `publication_generation` in the same SQL transaction as each publishable source closure, clock/closure change, cohort/stage transition, or source retirement; `_publication_revision` combines that generation with existing ready-file and downstream ACK-checkpoint identities, so the reducer wakes after a restart or changed SQL input.

The original `capture_record.utc_timestamp` is a query-only projection. Public output must still derive `time_ranges` from `ClockSegmentMap` and apply `_clear_unrepresentable_ranges` to an **entire range** when any record would overflow uint32; in that case all records in that range retain original device timestamps and the manifest has `utc: null`. Never write ready bytes by independently substituting each row's projected UTC value. Keep the existing `floor(timestamp + offset + 0.5)` rule and compare output byte-for-byte to the current overflow and boundary fixtures.

Quarantine has a separate typed disposition/retention FSM: unclassified evidence becomes `PUBLISHED_PREFIX` only after a certified checkpoint count/SHA and successful salvage eligibility, or `UNPROCESSABLE` after a typed reason; reclassification conflicts refuse. `PUBLISHED_PREFIX` means **internal draft-eligible custody**, not public ready custody. Its certified prefix points to the **same source rows**, with no copy; it remains eligible indefinitely below the ready threshold. A 72-hour retention sweep may remove terminal residual tail/conflict/opaque evidence only when no pending/cohort/ready-custody decision needs it; it cannot remove the certified prefix audio before full durable ready coverage. Both dispositions with insufficient age or live references keep evidence; expired unreferenced terminal evidence retires in a bounded SQL transaction. A nonterminal/unknown state refuses automatic deletion. This replaces old file-first `deletion_pending` and attempt cleanup intents with SQL-atomic row deletion; post-crash retry reads the authoritative row state. The `cleanup-attempts` CLI is removed or given a clearly typed SQL maintenance meaning, never a hidden file sweep. Test every state × age/reference condition and prefix salvage/restart semantics.

## Ready-output crash protocol

Before writing a public group, persist a stage intent keyed deterministically by its accepted cohort and bundle identity, including its frozen source slice geometry and time ranges for that output. Use one owned hidden staging directory/pair for the active group; the concrete current hard-kill risk is `ready_bundles._write_ready_group`'s hidden UUID directory, which `recover_capture_temporaries` does **not** reconcile because that function only covers capture-root staging. Read original DB rows by immutable accepted-source membership and keyset pages of at most `K` records, closing each SQLite read transaction and cursor before any ready-file write or fsync. The frozen source count/SHA and final output digest verify the complete stream; do not hold a DELETE-mode reader across slow output I/O or add persisted page hashes. Apply the existing UTC conversion and write `records.bin`, fsync it, write the unchanged canonical manifest, fsync the directory, rename to the final ready name, then fsync the ready parent. Only after this durable boundary commit the existing ready ledger identity/lineage, cohort cursor, coverage proof and `RETIRING` intent; then delete covered private rows in bounded restart-resumable transactions. Startup/retry first reconciles the deterministic stage and any already durable destination against the SQL intent, output hashes, manifest, and ledger. It may resume or rebuild only an **owned authenticated** incomplete stage; an unknown or unowned file/dir is preserved and causes a clear block. The output stage is removed after a finished group; there is never unbounded hidden scratch accumulation. Existing ready files are never rewritten, and ACK retirement remains ledger-first and exact-identity guarded. The bounded, old capture-root temporary recovery remains a distinct legacy-migration input; do not claim it covers ready-root scratch.

## Guarded one-way migration and deployment

Implement a version-1-to-2 stopped-service migration under `collector.lock`, using one transient same-filesystem candidate database. First inventory and fingerprint every old private attempt, draft, and quarantine file and relevant metadata; refuse unknown paths, changing identities, incomplete manifests, or unsupported opaque evidence without deleting them. Known quarantine symlinks are classified with `lstat`/exact `readlink` bytes and never followed; known opaque regular evidence is imported in bounded typed byte chunks with original path/inode/reason, size and SHA. Metadata alone never authorizes deleting opaque file content. An unknown directory shape, device/FIFO/socket, unreadable or changed entry stops **before activation** with exact relative path/type/size/reason and the missing decoder/classification. The next action is to extend and verify the bounded decoder or resolve its existing legacy lifecycle, then rerun inventory and parity; never delete an unexplained stray file just to retry. Classify legacy hidden ready-root `.bundle.<uuid>.tmp` separately: authenticate its naming, source draft and final-destination/ledger state; only a fully attributed redundant scratch may be removed by exact fingerprint after activation, otherwise preserve it and block with the same procedure. The existing capture-root temporary recovery is handled independently.

Open the canonical version-1 SQLite **read-write through SQLite** while stopped so its rollback journal is recovered by SQLite, validate its integrity and logical rows, and commit a distinct cutover receipt at `state(kind='migration', id='internal_audio_cutover')` containing one migration UUID, the sealed `source_revision` from the selected release's `share/omi-collector/release.json`, and exact inventory intent. The epoch/PID deployment-directory name and selector target are not receipt identity: a new directory with the same sealed revision resumes the same UUID, while a different revision fails stopped. A rerun adopts the existing source receipt UUID and inventory verbatim when the selected new release and current file fingerprints match; a mismatch fails stopped rather than minting a second cutover identity. The existing completed control-state migration marker at `state(kind='migration', id='current')` remains intact; this new receipt is transition state for forward recovery, not an old-runtime compatibility contract. Use `Connection.backup` to create the candidate after that source receipt; never copy only the main database file or discard a hot journal. Refuse if recovery/backup or post-recovery journal classification remains ambiguous. Authenticate each old manifest/checkpoint/raw byte stream, including any aligned suffix and bounded unaligned tail, then import source/ordinal rows and typed tail/conflict/evidence in bounded chunks. Preserve overlapping sources separately so equality/conflict and physical gaps remain testable. Import exactly one typed source per authenticated physical attempt/quarantine/draft artifact, and link each present `StateKind.ATTEMPT` or `StateKind.QUARANTINE` row to its descriptor, checkpoint, source, disposition/evidence and terminal facts without duplicating audio. After physical import, reconcile any registered row whose directory/entry is already absent from an old file-first cleanup crash window: authenticate the descriptor/checkpoint against its published draft or later ready lineage, or authenticate a zero-data terminal cleanup; only then drop that orphan row in the candidate transaction. Unknown rows, missing custody or mismatched lineage fail stopped. Preserve reason, entry kind, terminal state/time/reason and any move/delete intent for the rows that still own evidence. Reconcile old pending file operations or fail stopped. Delete both generic JSON row families **within the candidate transaction**; a version-2 runtime gate rejects residual rows, so there is no dual truth. Retain all other version-1 metadata unchanged. Before activation compare every retained logical row against the recovered canonical DB, every converted identity/disposition/terminal time against its old row, and candidate integrity plus per-source reconstructed byte count/SHA, checkpoint/frontier, source order, gap/overlap graph, closure/ready lineage, and ready bytes where a draft is already covered. Existing `_legacy_rows` parity alone is insufficient after the earlier control-state migration. Never use a memory-sized full raw read. Finalize the candidate's copied cutover receipt as `PREPARED`, with the same migration UUID, verified source logical digest, exact obsolete-file inventory fingerprint and cleanup intent; close both SQLite handles and require a classified clean journal state before activation. After candidate replacement, v2 schema plus the matching `PREPARED` receipt already mandates forward cleanup even if killed before the receipt is advanced to `CLEANUP_PENDING`; completion is recorded only after exact cleanup. The UUID and verified parity identify this candidate without a self-referential database-file hash. No sidecar receipt or archived legacy backend is introduced.

Preflight both migration and steady-state space using measured DB/index growth per exact row, reclaimable SQLite freelist pages, the worst bounded capture/UTC-refresh/retirement transaction's DELETE rollback journal, a full active public ready output copy, and configured safety headroom. Check DB/index/journal reserve on the DB filesystem and output-stage/copy reserve on the ready filesystem; if both roots share a device, add their simultaneous peaks rather than counting free space twice. Keep insertion and retirement transactions bounded (at most one writer drain for capture and a measured small row quantum for `RETIRING` deletion). SQLite may reuse freed pages; do not add a recurring VACUUM timer or assume the DB file returns pages to the filesystem. Report peak `page_count`, `freelist_count`, journal size, and free bytes in tests and live acceptance; if measured headroom is insufficient, stop before a consuming READ or output rather than promise a fixed multiplier.

The deploy wrapper stages and validates the new release, stops the service, then durably selects/fsyncs the **new** release and its parent directory **before** any version-2 canonical mutation. It invokes that selected release's single idempotent `migrate-state --internal` command, which acquires the stable lock. The command recovers canonical v1 through SQLite, adopts or creates a source receipt with migration UUID, sealed source revision, exact candidate path, migrator effective UID/GID, source digest, file inventory and `BUILDING` phase **before** candidate creation, authenticates old internal files, builds and parity-verifies the receipt-named `.collector-state.sqlite3.migrating.<uuid>` candidate, records its `PREPARED` receipt, then replaces canonical and fsyncs its parent. A pre-existing prepared candidate is adopted only when UUID, schema, receipt, source digest and obsolete-file fingerprints match. After a kill during `BUILDING`, the next invocation reauthenticates the still-intact canonical v1 and exact source inventory, identifies the owned non-symlink candidate by the source receipt's path/UUID and recorded migrator UID/GID, then removes only that partial candidate, fsyncs its parent and rebuilds it under the same UUID; an unknown, foreign-UID or changing candidate fails stopped. The installed wrapper currently invokes this migrator as root, so production candidate ownership is recorded as root; it assigns the activated canonical DB to the service/operator account only after exact cleanup. Schema v2 with the matching `PREPARED` or `CLEANUP_PENDING` receipt never rebuilds v1 and proceeds only to forward cleanup. After activation, the command revalidates recorded file identities/hashes, deletes **only** the exact obsolete private files/directories, fsyncs their parents, and marks cleanup complete. Canonical v1 remains unchanged before the new selector is durable; old private sources remain until parity is verified and exact cleanup finishes; none is archived after successful cleanup. An empty or absent provisioned attempt/quarantine/draft root is legal under v2; a nonempty unknown root fails closed.

The command returns zero only when schema v2, receipt and cleanup are complete; any nonzero migration exit leaves the selected new release and service stopped with a concrete migration-incomplete reason. The new service runtime maps an incomplete v1/v2 migration gate to distinct exit status 78, and the installed unit adds `RestartPreventExitStatus=78` while keeping ordinary `Restart=always` for unrelated failures. Boot therefore records one failed, non-restarting migration-required service until the next normal deploy/migration invocation; it never loops or opens BLE. After SIGKILL, reboot, or failed deploy, the next normal deploy/migration invocation inspects canonical schema, source/candidate receipt and exact file fingerprints under the same lock: v1 resumes candidate preparation/activation, while v2 resumes only forward cleanup. No runtime capture or BLE begins against v1 or an incomplete v2 receipt. There is no automatic boot-time migration executor and no old-release rollback path. A hard kill at canonical rename/parent-fsync may expose v1 or v2; the selected new release refuses capture in either incomplete state until that forward reconciliation succeeds. The deploy trap uses canonical schema/receipt and selected-release identity on every invocation rather than process-local flags or the current `state_file exists` shortcut; it never switches back once the new selector is durable. Unknown DB/candidate/journal identity fails stopped, without deleting unauthenticated files or creating an empty DB. Test SIGKILL before/after selector publication, source receipt, candidate preparation, canonical activation and each exact deletion; test stopped/refused service after interruption and successful forward resume on the next deploy. Version-1 import decoders are isolated transition code, not a selectable runtime backend.

Physical SQLite corruption is a fail-stop condition that preserves the database and its journal for recovery; do not claim that a row in the same damaged DB can quarantine it. Validate service-account read/write ownership and operator-group read-only access after candidate activation. The ready output tree and downstream `work/omi-ready-checkpoint.json` stay outside the internal migration. Do not touch production before the code, tests, peer review, PR, and protected release candidate pass.

## Finite implementation and verification sequence

1. **Pre-code measurements and fixtures.** Record the current largest configured batch, measured peak sustained BLE ingress in bytes/second, old writer drain/checkpoint latency, SQLite short-transaction latency for 1, 128 and 1,024 exact 444-byte rows under the same journal/sync settings both with per-call connection setup and with one writer-scoped persistent connection, peak arena/SQL buffer memory, and available disk headroom. Set the numeric gate from those measurements before implementation: p95 full-drain commit time must not exceed `(K * 444) / measured_peak_sustained_ingress_bytes_per_second` (and a 1-record drain is measured separately), peak writer lag `Q_peak` must stay below configured `arena_max_bytes` minus the largest admitted notification throughout the measured largest batch, and the queue must drain at its final barrier, and its final checkpoint/seal barrier must finish within configured `sync_timeout_seconds` (currently 60). Record all three observed values and limits, and reject/re-review this design if any fails; do not claim they pass in advance. Use owned local fixtures, not production mutations; report numbers as measurements, not assumptions. Build a version-1 mixed-source fixture with complete, partial, overlapping, gap, quarantine, and ready-covered cases and a frozen public ready pair.
