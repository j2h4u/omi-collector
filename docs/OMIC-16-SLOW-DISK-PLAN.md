# OMIC-16 slow-disk durability amendment

**Status: design for review, not implemented.** This amends the runtime wait policy of the [frozen OMIC-16 implementation plan](OMIC-16-IMPLEMENTATION-PLAN.md) without changing that artifact. The [implementation receipt](qa/2026-10-13-omic-16-implementation.md) records the measured candidate and release state. The host disk can be very slow under load: one exact-image 684,816-record replay completed, while an earlier replay reached the writer's 60-second barrier timeout and then its 30-second close timeout. The earlier run did not record an at-deadline queue or durable frontier, so its cause remains unknown. Elapsed time alone cannot establish that admitted storage work failed.

## Decision and custody boundary

Once the service admits bytes or a state transition, it owns the resulting SQLite work through completion, reconciliation, and worker join. No wall-clock deadline converts an in-progress durability operation into a timeout failure. Keep the existing BLE notification and command deadlines, bounded writer queues, space checks, real I/O-error classification, and fail-stop ambiguity handling. Preserve the order **admitted bytes → completed transaction → durable acknowledgment → permitted device advance**. Written or queued counts never substitute for a durable frontier. Cancellation and repeated cancellation wait for the owned result; they cannot abandon a worker that may still commit.

An external reader may delay SQLite admission indefinitely, so all service components that share the actual `StateDB` instance must serialize their own SQL access. Add one instance-owned reentrant access guard. Hold it from connection initialization or active SQL entry through full cursor consumption/closure, transaction completion, and any required ambiguous-commit inspection. Release it while a persistent connection is idle, during ready-file I/O, and between writer drains. Do not create a path-global lock or hold it for the writer's lifetime. Add a composition test that verifies the runtime injects the same `StateDB` into capture, staging, status, clock, quality, firmware, and maintenance.

For each runtime write transaction, acquire the guard and admit with `BEGIN EXCLUSIVE`. Retry only when the direct exception from that BEGIN has `error.sqlite_errorcode == sqlite3.SQLITE_BUSY` (integer 5) and `connection.in_transaction` is false, using the existing five-second SQLite busy handler per attempt. Do not match extended BUSY codes, LOCKED, wrapped causes, or error text. Execute the mutation and COMMIT exactly once after admission; preserve current rollback and authoritative ambiguity reconciliation. Do not retry DML or COMMIT, disable cache spill, change journal mode, add a general retry layer, or introduce a second-connection read inside a transaction. In DELETE journal mode, exclusive admission excludes a reader that could otherwise interrupt cache spill or COMMIT. Finish every cursor before releasing the guard. A local read-only `device status` or `device metrics` command may itself report busy while the service owns an exclusive transaction; that inspector result must not fail the service. A rogue external writer can still block connection setup before admission, and genuinely stuck external ownership requires operator intervention.

The stopped-service one-time migration and deployment helpers are separate from the runtime writer. Include the two canonical writable admissions in `internal_audio_migration.py` (`_recover_interrupted_fresh` and `_put_receipt`): reuse the same narrow `BEGIN EXCLUSIVE` exact-code admission helper, without adding a reentrant guard to this offline single-owner connection. An ordinary external read-only inspector may hold SHARED while the service is stopped; it must not turn a healthy canonical migration COMMIT into a five-second failure. Keep the native five-second SQLite connect/busy handler per admission attempt; it is not a filesystem-I/O deadline. Canonical read-only validation and connection setup retain finite lock-conflict reporting, since legitimate read-only callers are compatible and an actual EXCLUSIVE external writer violates stopped-service ownership. The private candidate build has no legitimate external contender. Do not add deadlines to the already-unbounded handoff child or service-stop subprocesses.

## Acceptance and release sequence

Use deterministic event-held tests, with no minute-long sleeps. Hold the shared database guard or a commit and request status, clock, quality, and read work concurrently: the event loop, failure latch, and in-memory status reads remain responsive, no same-process BUSY is induced, no durable acknowledgment appears early, and every operation completes after release. Prove the guard releases after raw cursor closure and does not span an idle persistent connection or ready-file I/O. Hold an external SHARED reader and confirm exclusive admission retries without entering a transaction or executing DML, then commits once; confirm a new reader cannot interrupt the owned write. Exercise cursor cleanup, exact rollback/commit/indeterminate reconciliation, exact-code retry selectivity, and a genuine I/O fault independently.

Cancel and re-cancel checkpoint, barrier, interruption, publication, and close while their worker is held; assert the exact committed frontier, no early device advance, bounded queue backpressure, and eventual worker exit after release. Test failed status persistence followed by an unchanged snapshot, concurrent update ordering and first-failure preservation. While progress-status persistence is blocked, verify the main loop still handles cancellation and other events without accumulating unbounded reporter tasks or losing lifecycle milestones. Test clock-intent order and reporter responsiveness. Send repeated TERM during a held commit and verify one ingress stop, no premature shutdown, then clean join; check the systemd infinite stop setting. Preserve the existing BLE-deadline tests and all source custody tests.

After focused checks, run the five project release gates on one frozen candidate: `just check`, `just unit`, `just crap-check`, `just docker-build`, and `just runtime-smoke`, in the assigned serial QA slot. Re-run the finite largest capacity scenario on its exact image, recording duration, durable frontier, queue occupancy, memory, and byte parity. A harness deadline means acceptance is incomplete, not that storage may abandon admitted work. The former 60-second barrier number is diagnostic rather than a hard acceptance limit under healthy slow storage. Real-pendant peak ingress, protected release, and live behavior remain separate required acceptance steps.

Normal `systemctl stop` may wait indefinitely for a disk or SQLite operation to finish. An operator who establishes a genuine deadlock may explicitly force SIGKILL; this can discard queued or uncommitted work after the last committed prefix. Restart must recover from committed custody, not infer success from the killed operation. Do not add an automatic stall alarm, watchdog, or alternate storage backend as part of this amendment.
