# OMIC-16 slow-disk durability amendment

**Status: revised design for review, not implemented.** This amends the runtime wait policy of the [frozen OMIC-16 implementation plan](OMIC-16-IMPLEMENTATION-PLAN.md) without changing that artifact. The [implementation receipt](qa/2026-10-13-omic-16-implementation.md) records the measured candidate and release state. The host disk can be very slow under load: one exact-image 684,816-record replay completed, while an earlier replay reached the writer's 60-second barrier timeout and then its 30-second close timeout. The earlier run did not record an at-deadline queue or durable frontier, so its cause remains unknown. Elapsed time alone cannot establish that admitted storage work failed. The first premium plan review returned NO-GO on connected callback, shutdown, and deployment boundaries; this revision addresses those design findings before implementation.

## Decision and custody boundary

Once the service admits bytes or a state transition, it owns the resulting SQLite work through completion, reconciliation, and worker join. No application wall-clock deadline converts an in-progress durability operation into a timeout failure. Keep the existing BLE notification and command deadlines, bounded writer queues, space checks, real I/O-error classification, and fail-stop ambiguity handling. Preserve the host order **admitted bytes → completed transaction → durable acknowledgment → permitted host-issued ADVANCE**. Written or queued counts never substitute for a durable frontier. Cancellation and repeated cancellation wait for the owned result; they cannot abandon a worker that may still commit. The host's existing 180-second systemd stop ceiling is a separate administrative force-stop boundary, described below.

An external reader may delay SQLite admission indefinitely, so all service components that share the actual `StateDB` instance must serialize their own SQL access. Add one instance-owned reentrant access guard. Hold it from connection initialization or active SQL entry through full cursor consumption/closure, transaction completion, and any required ambiguous-commit inspection. For reused autocommit publication readers, one guard scope covers one SQL page/query batch; close its cursor on success, exception, and early return before guard release or READY-file I/O. Retaining the idle connection is allowed, retaining a SHARED read transaction across file I/O is not. Release the guard while a persistent connection is idle and between writer drains. Do not create a path-global lock or hold it for the writer's lifetime. A mandatory runtime precondition rejects guard acquisition when `asyncio.get_running_loop()` succeeds on the calling thread; a removable debug `assert` or test bypass is insufficient. Track the owning writable connection per thread for both ordinary and persistent/raw transaction scopes. Before opening **or using** a different connection while the owner is in transaction, fail immediately; use of the yielded owner connection remains legal. Clear transaction ownership after confirmed COMMIT/ROLLBACK while retaining the outer guard for authoritative inspection or reopen. Add a composition test that verifies the runtime injects the same `StateDB` into capture, staging, status, clock, quality, firmware, and maintenance.

For each runtime write transaction, acquire the guard and admit with `BEGIN EXCLUSIVE`. The new admission helper retries only when the direct exception from that BEGIN has `error.sqlite_errorcode == sqlite3.SQLITE_BUSY` (integer 5) and `connection.in_transaction` is false, using the existing five-second SQLite busy handler per attempt. Do not match extended BUSY codes, LOCKED, wrapped causes, or error text. The helper never replays transaction bodies, DML, or COMMIT after admission; do not disable cache spill, change journal mode, or add a general retry layer. Preserve the seven existing bounded publication recovery state machines: after an operation error they terminate/rollback the transaction and inspect authoritative durable state. Adopt the exact proposed state without replay; only a confirmed old state permits their already-defined single retry; a third or unreadable state fails stop. Do not add or widen these loops or retry by elapsed time or exception wording. Never introduce a second-connection read inside an active transaction. In DELETE journal mode, exclusive admission excludes a reader that could otherwise interrupt cache spill or COMMIT. Finish every cursor before releasing the guard. A local read-only `device status` or `device metrics` command may itself report busy while the service owns an exclusive transaction; that inspector result must not fail the service. A rogue external writer can still block connection setup before admission, and genuinely stuck external ownership requires operator intervention.

Make the generic owned-await helper cycle-free and preserve the **actual settled outcome** after repeated cancellation. If owned work succeeds, re-raise the saved cancellation after joining it; if it fails, raise that original worker exception directly. Do not convert a fatal storage result into a cancellation cause or an optional timeout. At the application cleanup boundary, retain the first already-observed fatal error over later cleanup faults; a fatal cleanup result outranks a previously observed cancellation or nonfatal error. The helper itself neither classifies storage errors nor walks causes. Confirmed corruption must still reach the CLI's exit-78 path.

When a synchronous callback can return an awaitable, own its offloaded invocation **and** the returned awaitable as one shielded compound task. Cancellation during invocation must not discard a coroutine that has not yet been awaited or silently skip a lifecycle milestone. The same ownership transfer matters for offloaded factory results: if quality construction created a worker before cancellation or another error, retain its settled result and close/join that worker before unwinding; a partially failed factory closes any worker it created. Preserve the primary/fatal precedence above.

Constructor-only StateDB retention and in-memory reducers do not require a thread hop. The guard's mandatory no-loop check plus connected held-guard tests are the backstop; a text search alone is not acceptance.

The stopped-service one-time migration and deployment helpers are separate from the runtime writer. Include the two canonical writable admissions in `internal_audio_migration.py` (`_recover_interrupted_fresh` and `_put_receipt`): reuse the same narrow `BEGIN EXCLUSIVE` exact-code admission helper, without adding a reentrant guard to this offline single-owner connection. An ordinary external read-only inspector may hold SHARED while the service is stopped; it must not turn a healthy canonical migration COMMIT into a five-second failure. Do not add deadlines to the already-unbounded handoff child or service-stop subprocesses.

## Acceptance and release sequence

Use deterministic event-held tests, with no minute-long sleeps. Hold the shared database guard or a commit and request status, clock, quality, and read work concurrently: the event loop, failure latch, and in-memory status reads remain responsive, no same-process BUSY is induced, no durable acknowledgment appears early, and every operation completes after release. Fill the quality queue while storage is held; repeated overflow has O(1) pending state and BLOCK persists before later CLEAR and close. Exercise publication-completion status, progress-status persistence, and clock-state emission under the same hold without unbounded callback tasks. Repeated firmware-error reports must keep exactly one owned pending relay and drain at close; fatal completion must reach the first-fatal owner. Hold READY file I/O after a publication page fetch and confirm its cursor closed and an independent DB writer proceeds; cover exception/early-return cursor closure too. Test new and preexisting second connections inside EXCLUSIVE fail before SQL, nested StateDB reads fail, same-owner queries succeed, and a new inspection connection is legal after rollback. Hold an external SHARED reader and confirm exclusive admission executes zero DML until acquired, then commits once; confirm a new reader cannot interrupt the owned write. For existing publication reconciliation, count body/COMMIT attempts: proposed state has one, confirmed old has at most two, third/unreadable has no retry, and CORRUPT is immediately fatal. Exercise exact-code retry selectivity, the loop-thread precondition, and a genuine I/O fault independently.

Cancel and re-cancel checkpoint, barrier, interruption, publication, and close while their worker is held; assert the exact committed frontier, no early host-issued ADVANCE, bounded queue backpressure, and eventual worker exit after release. Then make owned work raise CORRUPT after two cancellations and verify the original fatal reaches CLI exit 78; a clean owned result preserves ordinary interruption. Test a synchronous callback that returns an awaitable while cancellation arrives during the offloaded invocation: own invocation and awaiting its result as one shielded compound task, so no coroutine or lifecycle milestone is abandoned. Test failed status persistence followed by an unchanged snapshot, concurrent update ordering and first-failure preservation, including first fatal versus a later cleanup fatal. Make quality construction fail before a worker exists while the DB guard is held: the loop handles heartbeat/TERM, then BLOCK persists on release, with no phantom worker. Cancel while CONFIGURED persistence is held after quality worker creation and verify the settled factory result is retrieved and its worker closed/joined. Hold clock-intent persistence beyond the former preflight deadline: there is no storage cancellation or premature RTC write; after release, stale-target detection defers the optional correction and resolves intent conservatively. Hold storage-backed telemetry emission similarly, while real BLE and host-probe timeouts still fire. While progress-status persistence is blocked, verify the main loop handles other events without unbounded reporter tasks or lost lifecycle milestones.

Hold synchronous startup persistence and send TERM, then send TERM again during async cleanup: one StopIntent prevents the existing readiness event and any new BLE/RTC/READ/ADVANCE admission, while admitted work settles. Test TERM and INT before task attach, at the attach seam, after attach, and repeatedly during cleanup: the same installed handlers observe one intent and schedule at most one root cancellation. Force-exit a subprocess during held pre-commit storage, reopen the exact committed prefix, and run both fresh-device-cursor outcomes: retained bytes replay exactly once; cursor-ahead loss records the exact missing interval without invented bytes, then continues from the fresh cursor. No early host-issued ADVANCE is allowed, but it is not a lossless guarantee. Verify the normal 180-second systemd stop setting remains and test delayed startup readiness through the connected deployer: it waits without an elapsed failure while the same PID/invocation/restart state remains active or activating, even if the journal event is late. A restarted unit with a new invocation is a confirmed identity change even if PID is reused. An observation failure or deployer interruption does not stop a confirmed selected release with the same live invocation; a confirmed failed/exited/restarted unit or ambiguous selector enters forward recovery. Keep `Type=exec`, preserving the old-runtime rollback path. Check that runtime health and QA smoke do not treat a separate read-only inspector's BUSY result as service failure. Reject retired writer/firmware close-timeout TOML keys and remove stale port arguments and timeout-only exception paths. A read-only parse of the current installed service config found neither retired key, so no live config rewrite is needed; a future supplied key still fails fast. Preserve the BLE `sync_timeout_seconds=60` as a transport budget outside post-DONE durability; retain the nonstorage BLE observer-join and PHY reap timers. Preserve all custody tests.

After focused checks, run the five project release gates on one frozen candidate: `just check`, `just unit`, `just crap-check`, `just docker-build`, and `just runtime-smoke`, in the assigned serial QA slot. Re-run the finite largest capacity scenario on its exact image, recording duration, durable frontier, queue occupancy, memory, and byte parity. A harness deadline means acceptance is incomplete, not that storage may abandon admitted work. The former 60-second barrier number is diagnostic rather than a hard acceptance limit under healthy slow storage. Real-pendant peak ingress, protected release, and live behavior remain separate required acceptance steps.

Normal TERM asks the process to stop ingress and join admitted work without an application storage deadline. The existing `TimeoutStopSec=180s` remains the host's finite forced-stop boundary for ordinary stop, deployment's stop/restart of the old runtime, and UPS-triggered shutdown or reboot. At that boundary systemd can SIGKILL a still-slow or stuck process; an operator can also force-kill explicitly. Only the actually committed frontier is durable. Uncommitted audio may be **permanently lost**: stock firmware can advance its cursor on BLE transmission confirmation before host persistence, even if this host has not sent ADVANCE. Restart must recover the committed prefix and use fresh device INFO to distinguish retained/replayable bytes from a cursor-ahead interval; the existing confirmed-loss ledger records the latter exactly. No lossless force-stop guarantee is made. The 180 seconds is not a storage-success classification or a reason for the application to claim custody. Do not change host UPS configuration, add an automatic stall alarm, watchdog, or alternate storage backend as part of this amendment.

If readiness observation is interrupted but the selected release and same live invocation are confirmed, report **selected, unverified, running**, exit nonzero (INT 130, TERM 143, other observation failure 1), skip release pruning, retain selected release and recovery evidence, and remove only owned disposable scratch. Never report deployment success in that state. Later verification uses the existing read-only selector, service snapshot, journal event/config match, and six-second stability predicates against the retained release; it does not rebuild, migrate, or restart merely to verify. An identity change leaves the earlier attempt unverified and requires explicit evaluation of the new invocation. Mark the current release verified only after all predicates pass; prune retained artifacts only through ordinary safe cleanup or a successful later deployment. No new persistent deploy state machine or CLI flag is needed.
