# План перехода Omi на draft → ready → speech

**Статус: предложенный план; изменения не реализованы.** Решения ниже рекомендованы по результатам экспертной панели. Создание этого документа не разрешает и не выполняет миграцию. Область: один кулон, один Collector, один Windmill consumer; код Collector и omi-pipeline, данные `/srv/pipelines/omi`.

## Результат для пользователя

Collector будет хранить незавершённую запись в raw draft, один раз готовить неизменяемый ready bundle и передавать его Windmill. Windmill будет выдавать обычный Ogg с одним логическим потоком и паспортом. Постоянная копия captured объёмом около 1,4 ГБ, полные поколения и служебные VAD Ogg больше не нужны. Уже полученные 12 пар speech Ogg + паспорт сохраняются без изменения.

Аудио с неопределимым временем также попадёт в ready: в паспорте будет `UTC=null`, исходное время устройства и относительное положение в записи. Уникальное необработанное аудио не удаляется по возрасту. Готовый источник удаляет только Collector, когда Windmill надёжно подтвердил использование всего bundle; незакрытый речевой хвост удерживает нужные источники.

## Рекомендуемые правила данных

### Две зоны Collector и одно подтверждение Windmill

| Объект | Правило |
| --- | --- |
| `draft` | Исходные records без изменения raw timestamps; ещё не финализированные данные и достаточные метаданные восстановления |
| `ready` | Один неизменяемый bundle с manifest, диапазонами и digest: известное время скорректировано; при unknown timestamp bits остаются исходным device time, manifest указывает `UTC=null` для сегмента |
| Producer ledger | Компактное долговечное состояние публикации и удаления; предотвращает повторную публикацию уже подтверждённого bundle после рестарта |
| Windmill checkpoint | Одно долговечное состояние продвижения, VAD decisions, packet ranges и открытого речевого хвоста |
| ACK | Долговечное подтверждение точного bundle и его digest; возникает только после полного использования источника |
| Speech result | Обычный single-stream Ogg и паспорт, согласованно зафиксированные до ACK источников |

Producer ledger и checkpoint — необходимые состояния восстановления, а не дополнительные копии аудио. Не вводить универсальный протокол, версии поколений, второй consumer, совместимость со старым layout или fallback.

### Публикация и удаление

1. Collector записывает raw records и recovery metadata в draft и обеспечивает их долговечность. Явный `ADVANCE` допустим только после этого; ACK Windmill для него не требуется.
2. Collector собирает **один** ready bundle во временном расположении на том же filesystem. Проверяет границы и digest, выполняет необходимые `fsync`, публикует атомарным rename и фиксирует каталог.
3. Collector долговечно отмечает публикацию в producer ledger, затем удаляет соответствующий draft. После успешной публикации постоянной raw-копии нет.
4. Windmill читает flat ready, сохраняет решения VAD и packet ranges в одном checkpoint. Источник остаётся доступным до завершения всех результатов, которые от него зависят.
5. Windmill долговечно фиксирует Ogg и паспорт, затем checkpoint и ACK точного источника. Для `no_speech` долговечно фиксирует решение и ACK без пустого Ogg.
6. Collector проверяет ACK и digest, долговечно фиксирует разрешение удаления/завершённое состояние в producer ledger, затем удаляет ready. Повторное выполнение после сбоя безопасно; удалённый bundle не публикуется снова.

Восстановление должно согласовывать уже опубликованный ready с draft и ledger: сбой между rename, записью ledger и удалением draft не должен ни терять данные, ни создавать второй bundle. Сбой между выпуском speech и ACK не должен создавать второй speech result. Для этого использовать устойчивую идентичность по источникам и packet ranges в существующем состоянии, без отдельного сервиса транзакций.

ACK означает, что **все** packets источника либо вошли в долговечный результат, либо имеют долговечное решение об отсутствии речи. Завершённый VAD при открытом речевом хвосте ещё не означает ACK: нужные bundles удерживаются до настоящей тишины или подтверждённого разрыва источника. Смена часовой эпохи сама по себе не является тишиной.

### Время без выдуманного UTC

Нынешняя clock correction начинается с `INFO.write_sequence` и применяется лишь к `[write_before, write_after)`: она пропускает ранний backlog и может затронуть новые records после установки RTC. Кроме того, offset считается от более позднего target для `SET_TIME`, а не от host time при чтении RTC. Healthy RTC observations сейчас не сохраняются.

Рекомендуется сохранять **все** RTC observations, включая healthy, пока они могут относиться к незавершённым сегментам. Observation содержит device RTC, host timestamps до/после чтения и доступные границы последовательности. Для сегмента с подтверждённой принадлежностью к этой часовой эпохе:

`UTC ≈ raw_timestamp + (host_midpoint_at_RTC_read − device_RTC_at_read)`.

Это оценка с неопределённостью интервала чтения, а не обещание точности до миллисекунды. Более поздний target `SET_TIME` не подменяет host midpoint. Применимость определяется принадлежностью к clock segment, а не только тем, попал ли record в окно команды записи. Backlog, уже существовавший до observation, может использовать эту оценку только при подтверждённой непрерывности той же эпохи. Records после `SET_TIME` не получают offset предыдущей эпохи; неоднозначная граница остаётся unknown.

Протокол не сообщает boot ID или uptime кулона. Поэтому для некоторых старых records невозможно установить точное UTC и даже безопасно связать их с текущей RTC observation. Не восстанавливать такую связь догадкой по близким timestamps или одному порядку получения.

Manifest ready сохраняет raw device time, его привязку к records/segments, последовательность и sample-relative timing, известные разрывы, статус времени и использованные observations/преобразования. При unknown исходные timestamp bits в records не меняются и означают время устройства; manifest указывает `UTC=null` для соответствующего сегмента. Это явное исключение из требования «ready уже исправлен»: корректное UTC получить невозможно, и сохранённое device time не является нормализованным UTC. Конечный паспорт сохраняет эту неопределённость. При смешанном результате статус отражается по сегментам, а единый абсолютный диапазон не придумывается. Windmill работает по packets, samples и sequence; календарный скачок не превращается в добавленную тишину.

Ready финализируется и при unknown, после чего неизменяем. Поздняя observation не запускает переписывание ready и новое поколение. Нужную provenance из historical clock-import ledger/repairs следует перенести до их удаления; отсутствие provenance нельзя заменить сохранением старого предположительного UTC.

### Временные файлы и нехватка места

Для VAD использовать packets или анонимный/короткоживущий временный Ogg только там, где он нужен существующему декодеру. Отмена и `SIGKILL` не должны оставлять постоянные VAD Ogg; именованные остатки чистятся при восстановлении до повторного запуска обработки. Это не speech results.

Срок 72 часа допустим только для отладочных материалов и завершённых попыток. Он не применяется к draft, уникальному необработанному ready, источникам открытого хвоста, необходимым ACK/ledger/checkpoint или speech results. После долговечного ACK ready удаляется при ближайшем проходе Collector, без ожидания 72 часов.

Если диск заполнен, а Windmill не освобождает источники, Collector приостанавливает `READ`/`ADVANCE` и сообщает причину. Кольцевой буфер кулона при этом может перезаписать ещё не прочитанное аудио: конечный локальный диск не даёт бесконечной гарантии хранения. Кроме того, firmware `READ` уже продвигает курсор до локального `fsync`; остаётся окно потери при сбое между чтением и долговечной записью. Переработка хранения не устраняет этот риск протокола.

## Последовательность реализации и перехода

### Фаза 1. Подготовить согласованную пару Collector + Windmill

- [ ] Проследить существующий поток READ → draft → clock normalization → ready → VAD → speech → checkpoint и использовать имеющиеся примитивы записи/восстановления.
- [ ] Реализовать в Collector две зоны, сохранение RTC observations, явное unknown UTC, однократную финализацию и producer ledger с восстановлением после прерываний.
- [ ] Реализовать flat ready consumer Windmill, один checkpoint, VAD decisions/packet ranges, долговечный ACK и удержание источников открытого хвоста.
- [ ] Сделать Collector единственным владельцем удаления ready, включая обработку сохранённых ACK после рестарта.
- [ ] Убрать создание полных `.generations/current` snapshots, постоянного captured-дубля и постоянных VAD Ogg. В коде удалить historical clock-import CLI и его runtime path, сохранив автоматическое штатное восстановление Collector; старый production ledger оставить до переноса нужной provenance.
- [ ] Подготовить одноразовый перенос проверенного checkpoint и путей. Не создавать постоянный migration framework или новый слой совместимости.

**Go:** обе части реализуют один контракт и проходят целевые сценарии ниже. **Stop:** любая часть ещё требует старое поколение, удаляет источник без ACK, блокирует ready из-за unknown UTC либо нуждается в полном копировании данных.

### Фаза 2. Проверить release candidate обеих частей

Во время разработки запускать проверки затронутых сценариев; полные gates — для согласованного release candidate. Ни один gate не ослаблять ради прохождения.

- [ ] Collector: `just check`, `just crap-check`, `just unit`, `just docker-build`; `just runtime-smoke` при изменениях Docker runtime.
- [ ] Windmill/omi-pipeline: применимые gates соответствующего репозитория и проверка реального способа запуска flow.
- [ ] Пройти сценарную матрицу и recovery smokes на ограниченных данных, включая перенесённый checkpoint и неизвестное время.
- [ ] Подготовить согласованные релизы и порядок deploy обеих частей до остановки production. Удалить временные тестовые ресурсы после проверки их принадлежности.

**Go:** текущие кандидаты Collector и Windmill прошли обязательные gates и совместный smoke. **Stop:** потеря/повтор packets, изменение 12 сохранённых результатов, несовместимое состояние восстановления или любой провал gate.

### Фаза 3. Остановить изменения и зафиксировать окончательную ведомость

- [ ] Проверить, что watcher остаётся выключенным; остановить или дождаться завершения всех jobs, работающих с источниками, checkpoint и speech.
- [ ] Остановить Collector и убедиться, что writers больше нет. Только теперь зафиксировать конечные количества, границы, размеры и hashes.
- [ ] Сверить каждый ready bundle с captured с учётом известных repairs; повторно подтвердить уже проверенные преобразования timestamps двух bundles и сохранить нужную provenance.
- [ ] Вычислить точное объединение уже представленных и уникальных captured records: полные дубли отделить от частичных перекрытий по содержимому, а не только по sequence. Сохранить весь уникальный хвост для draft.
- [ ] Проверить e4a4 checkpoint целиком: все queue hashes, frontier/packet position, VAD decisions, ссылки и открытый speech tail. Подтвердить, что каждый используемый packet присутствует в конечном источнике.
- [ ] Зафиксировать hashes всех 12 speech Ogg + паспортов и убедиться, что перенос не приведёт к их повторному выпуску.
- [ ] Проверить одинаковый filesystem для исходного и нового ready, свободное место для одного собираемого bundle, метаданных и обычной обработки. Проверить пригодность существующего системного backup для отката после разрушительного этапа; новый полный backup не создавать.

**Go:** каждый уникальный record имеет целевое место, checkpoint полностью объясним, никаких writers нет. **Stop:** непонятное расхождение payload, конфликтующие records на одной позиции, отсутствующий источник checkpoint, неизвестная судьба уникального хвоста или необходимость cross-filesystem копии. Снимок из начала документа не заменяет эту проверку.

### Фаза 4. Перенести данные без гигабайтной копии

- [ ] Переместить существующие проверенные готовые bundles в flat ready через same-filesystem rename: ожидаемое исходное количество — 96, фактическое берётся из frozen inventory. Не копировать дерево и не создавать новое полное поколение.
- [ ] При переносе сохранить canonical payload и сформировать требуемые manifest/provenance и producer ledger. Уже нормализованный payload не пропускать повторно через clock repair. Старый timestamp не считать достоверным UTC только потому, что он присутствует в готовом файле.
- [ ] Перенести уникальный captured tail в draft; при частичном перекрытии оставить только уникальные records. Сверить record/payload coverage до и после; известные полные дубли не публиковать снова.
- [ ] Перенести полностью проверенный e4a4 checkpoint в единственное рабочее состояние, изменить ссылки на источники и перенести открытый tail. Сохранить frontier и packet position; не начинать обработку с нуля и не объединять два старых checkpoints эвристикой.
- [ ] Повторно проверить digests, границы, provenance и все ссылки checkpoint после rename. Зафиксировать метаданные на диске до запуска writers.

**Go:** новое размещение представляет ровно то же уникальное аудио и прогресс consumer; 12 результатов имеют исходные hashes. Два известных преобразования timestamps уже проверены и допустимы после повторной сверки в фазе 3. **Stop:** обнаружено неожиданное изменение payload/timestamps сверх этих проверенных преобразований либо требуется полная повторная нормализация. Такой случай сначала разбирается на конкретном bundle; обход через полную копию не допускается.

До удаления старых данных откат требует обратного переноса путей и согласованного восстановления состояния обеих частей. После начала новых записей нельзя просто вернуть прежний бинарник.

### Фаза 5. Запустить и проверить совместный поток

- [ ] Развернуть согласованную пару; сначала запустить Collector с новым состоянием и проверить восстановление/публикацию без дублей. Watcher оставить выключенным.
- [ ] Выполнить один контролируемый запуск Windmill с перенесённым checkpoint. Проверить продвижение из прежней позиции, включая открытый хвост, речь и `no_speech`.
- [ ] Проверить, что speech Ogg воспроизводится как один обычный логический поток, паспорт соответствует packet ranges и времени, а unknown остаётся `null`.
- [ ] Проверить порядок durability → ACK → удаление Collector и сохранение источников незавершённого хвоста. Проверить рестарт обеих частей без повторной публикации и повторного speech.
- [ ] Сверить покрытие records/packets: уже подтверждённые, удерживаемые открытым хвостом и ещё не обработанные диапазоны образуют согласованную картину без потери или повторного использования. Повторно сверить 12 исходных пар.

**Go:** поток проходит от нового draft до долговечного speech/`no_speech` и удаления подтверждённого ready, checkpoint восстанавливается. **Stop:** повтор, пропуск, ложное UTC, преждевременное удаление, многопоточный/chained Ogg или неожиданный рост постоянных копий. Остановить обоих writers и разбирать сохранённое состояние, не сбрасывать checkpoint.

### Фаза 6. Удалить подтверждённые остатки и завершить переход

- [ ] Удалить только те captured originals, чья полезная информация уже покрыта ready/draft либо подтверждённым результатом, а нужная provenance сохранена. Дубли и уникальные хвосты проверяются отдельно.
- [ ] Удалить устаревшие production generation metadata/checkpoints, старый historical clock-import ledger и временные migration scripts после успешного переноса необходимого состояния/provenance. CLI и runtime path уже удалены из кода в фазе 1. Не удалять новый producer ledger, ACK или единственный checkpoint.
- [ ] Удалить только созданные для задачи временные ресурсы. Уже удалённые поколения и 111 VAD Ogg не включать в обещанное дополнительное освобождение места.
- [ ] Включить watcher после успешного контролируемого запуска и очистки; проверить следующий штатный запуск, состояние Collector, свободное место и отсутствие VAD-остатков.
- [ ] Обновить эксплуатационную документацию, включая `docs/BEST_PRACTICES.md`: новый lifecycle, диагностика unknown UTC, ACK/open tail, disk-full и ограничение firmware READ.

**Завершено:** две зоны Collector работают, один Windmill checkpoint продолжает прежний прогресс, все 12 исходных пар сохранены, новые результаты корректны, постоянных captured/generation/VAD-копий нет. Старые данные удалены только после сверки. После разрушительной очистки rollback опирается на существующий системный backup и согласованное восстановление обеих частей; запуск старого бинарника не является rollback.

## Обязательные сценарии проверки

| Сценарий | Критерий принятия |
| --- | --- |
| Backlog до RTC observation в подтверждённой эпохе | Offset относится к правильному сегменту, включая ранний backlog; используется host midpoint при чтении |
| Healthy RTC observation и рестарт до финализации | Observation сохраняется и остаётся доступной нужным unfinalized segments |
| Старый backlog после reboot с неопределимой эпохой | Ready публикуется с raw time и `UTC=null`, без бесконечного удержания в draft |
| `SET_TIME`, records до/после команды, неоднозначная граница | Старый offset не попадает в новую эпоху; неизвестная принадлежность не выдаётся за UTC |
| Clock discontinuity при непрерывном звуке | Нет синтетической тишины, потери packets или ложного закрытия tail только из-за часов |
| Сбой после raw write, ready rename, ledger commit или draft delete | После восстановления ровно одно представление уникального аудио; нет повторной публикации |
| Полный дубль и частичное перекрытие | Подтверждённые одинаковые records учитываются один раз; уникальные части сохраняются; конфликт содержания останавливает обработку |
| Речь проходит через несколько bundles и остаётся открытой | До закрытия результата зависимые источники не ACK-аются и не удаляются |
| `no_speech` | Долговечное решение и точный ACK; нет пустого Ogg; Collector освобождает источник |
| Сбой после Ogg, до паспорта, после результата, до/после ACK | Неполный результат не разрешает удаление; восстановление не выпускает дубль; ACK требует точного digest |
| `SIGKILL`/отмена во время VAD | Источник сохранён; восстановление работает; постоянных временных Ogg нет |
| Перенос e4a4 checkpoint и открытого tail | Все ссылки/queue hashes валидны; прежняя позиция сохранена; 12 старых пар не меняются и не дублируются |
| Windmill недоступен и диск заполнен | Нет age-based удаления уникального аудио; READ/ADVANCE приостановлены; причина видна оператору |

## Разрешённые разногласия панели

| Вопрос | Рекомендуемое решение и причина |
| --- | --- |
| Ждать точного времени или финализировать unknown? | Финализировать ready с `UTC=null`: boot ID/uptime отсутствуют, поэтому ожидание может быть бесконечным и не добавляет точности |
| Кто удаляет готовый источник? | Только Collector после точного долговечного ACK Windmill: один владелец lifecycle и один механизм восстановления |
| Удалять через 72 часа или после использования? | Уникальное аудио — только после ACK; 72 часа — для debug/завершённых попыток. Возраст не подтверждает обработку |
| Перенести checkpoint или сбросить? | Перенести e4a4 после полной проверки: его queue соответствует источнику; сброс повторно обработает уже использованные packets |
| Сделать новое поколение/backup-копию или переместить? | Same-filesystem rename готовых bundles и перенос только уникального хвоста; существующий системный backup используется для rollback после очистки |

Все решения в документе остаются предложением до реализации, прохождения gates и выполнения соответствующего этапа перехода. Сейчас выполнено только составление плана.
